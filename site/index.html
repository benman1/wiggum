Start it. Read the diff when it's done.

Wiggum wraps Claude Code in a loop that plans a change, implements it one task at a time, runs your project's own verify commands, fixes what fails, and commits as it goes. You start it from the shell and read the diff when it's done.

docs/csv-export_plan.md
- [ ] Add a CSV serializer for report rows
- [ ] Stream the export instead of buffering
- [ ] Wire the download button to the endpoint
- [ ] Cover empty and 10k-row reports
git log --oneline
4e91c2a serialize report rows as CSV
b7d0f18 stream the export rather than buffering it
1a5c86e wire the download button to the export endpoint
93fb204 cover empty and large report exports
c02e7dd summarize the CSV export run
$ wiggum plan issues/csv-export.md && wiggum execute docs/csv-export_plan.md

Two commands. Read the plan in between and edit it — it's just markdown checkboxes.

What a run actually does

Four phases, in order. Wiggum prints them as it goes, so you can read a run's log and know where it stopped.

Phase 1

Diagnostic & status sync

Reads the repository against the plan and ticks off anything already done. Re-running a plan is cheap because this phase reconciles it first.

Phase 2

Implement, verify, fix

One task per iteration. After each, your verify commands run in order; a failure goes back to Claude with the error output until it passes or the retry budget runs out. Then it commits.

↺ repeats until the boxes are ticked, the run stalls, or it hits max_iterations
Phase 3

Summary & alignment

Reconciles the plan against what was built, writes a summary of what landed, what was deferred, and why the run stopped.

Phase 4

Documentation update

Optional. Pass --update-docs and it revises the files you name against what changed.

It verifies with your tools, not its own opinion

Wiggum has no idea whether your code is correct. It runs the commands you already trust and reads their exit codes.

.wiggumrc
# wiggum's own config, verifying wiggum
verify = shellcheck -s bash lib/wiggum.sh
verify = bats test/wiggum.bats
autofix = shfmt -w .

max_iterations = 30
max_validation_retries = 5

A waterfall, not a checklist

Steps run in the order you write them and stop at the first failure, so a type error never costs you a full test run.

Autofix runs first

An autofix step gets one chance to correct itself before Claude is asked to look at it. Formatters fix formatting; Claude fixes logic.

Retries are capped

A step that can't be fixed stops the run instead of burning tokens against it. wiggum check runs the same waterfall on demand.

Start it, walk away, keep watch

Runs last hours. wiggum top lists every run on the machine — whichever project it was started from.

wiggum execute <plan> -bRun detached and get the shell back.
wiggum watch <plan>Stream a run's output and block until it finishes.
wiggum kill <plan>Stop that run's process tree, and nothing else.

Install

One script. It copies the library, symlinks the CLI, and installs the /wiggum skill for Claude Code.

$ git clone https://github.com/benman1/wiggum.git && cd wiggum && ./install.sh

Then wiggum init in any project to generate a .wiggumrc from what it finds there.
